# Мониторинг системы "Jewerly Store System"

## Мотивация  

Внедрение мониторинга в систему "Jewerly Store System" критически важно для обеспечения стабильной работы, масштабируемости и улучшения клиентского опыта. С момента подключения API для заказов, данные Яндекс Метрики перестали давать полное представление о работе системы. Мониторинг позволит:

- **Выявлять и оперативно устранять проблемы:**  
  Мониторинг в реальном времени позволит обнаруживать аномалии и сбои до того, как они повлияют на клиентов. Это снизит количество просроченных заказов, потерянных контрактов и жалоб.  
- **Оптимизировать производительность:**  
  Мониторинг позволит выявить узкие места в системе, такие как медленный расчет стоимости, перегруженная очередь сообщений или неэффективные запросы к базе данных. Это позволит оптимизировать систему и повысить ее производительность.  
- **Принимать обоснованные решения:**  
  Данные мониторинга предоставят информацию, необходимую для принятия обоснованных решений о масштабировании, оптимизации кода, улучшении инфраструктуры и т.д.  
- **Улучшить клиентский опыт:**  
  Мониторинг позволит отслеживать ключевые показатели, такие как время обработки заказов, количество успешных заказов и скорость ответа API. Это позволит улучшить клиентский опыт и повысить лояльность клиентов.  
- **Снизить операционные расходы:**  
  Мониторинг позволит автоматизировать процесс обнаружения и устранения проблем, что снизит нагрузку на команду поддержки и уменьшит операционные расходы.  
- **Оценить эффективность изменений:**  
  При внесении изменений в систему, мониторинг позволит оценить их влияние на производительность и стабильность. Это позволит принимать более эффективные решения по развитию системы.  

## Обоснование для бизнеса:

Внедрение мониторинга - это инвестиция в стабильность, масштабируемость и прибыльность бизнеса. Затраты на мониторинг компенсируются снижением убытков от сбоев, повышением производительности, улучшением клиентского опыта и снижением операционных расходов. Предоставление API для заказов требует более глубокого контроля и мониторинга системы, чем раньше, чтобы обеспечить бесперебойную работу и высокое качество сервиса для партнеров.  

## Выбор подхода к мониторингу

Для разных частей системы я предлагаю использовать разные подходы к мониторингу:

- **Для API (Shop API, CRM API, MES API): RED (Requests, Errors, Duration)**  
  - Обоснование: RED - это подход, ориентированный на пользователя. Он позволяет быстро оценить качество работы API с точки зрения клиента, измеряя количество запросов, количество ошибок и время отклика.  
- **Для инфраструктуры (EC2, Databases, RabbitMQ, S3): USE (Utilization, Saturation, Errors)**  
  - Обоснование: USE - это подход, ориентированный на ресурсы. Он позволяет выявить узкие места и перегрузки в инфраструктуре, измеряя утилизацию ресурсов (CPU, memory, disk), насыщение ресурсов (очереди, connections) и количество ошибок.  
- **Для онлайн-магазина: Четыре золотых сигнала (Latency, Traffic, Errors, Saturation)**  
  - Обоснование: Необходимо отслеживать пользовательский опыт и основные параметры работы веб-приложения.  

## Отслеживаемые метрики

При планировании мониторинга системы "Jewerly Store System", мы будем отслеживать следующие ключевые метрики, сгруппированные по компонентам системы. Для каждой метрики указано ее назначение и необходимость использования ярлыков (labels) для более детальной аналитики.

1. **RabbitMQ (Очередь сообщений):**  

   - **Number of dead-letter-exchange letters in RabbitMQ:**  
     Эта метрика необходима для обнаружения проблем с доставкой сообщений. Большое количество сообщений в dead-letter-exchange может указывать на ошибки в коде обработки сообщений или неправильную конфигурацию.  
     - Ярлыки: exchange_name, routing_key – для идентификации конкретных проблемных маршрутов.  
   
   - **Number of message in flight in RabbitMQ:**  
     Эта метрика позволяет мониторить нагрузку на очередь и выявлять перегрузки. Резкий рост количества сообщений может указывать на проблемы с производительностью или блокировку потребителей.  
     - Ярлыки: queue_name – для анализа нагрузки по конкретным очередям.  

2. **API Services (Shop API, CRM API, MES API):**  

   Для API сервисов мы будем использовать подход RED (Requests, Errors, Duration), отслеживая:

   - **Number of requests (RPS - Requests Per Second):**  
     Оценка нагрузки на API, определение пиковых периодов для планирования масштабирования.  
     - Ярлыки: endpoint, method – для анализа нагрузки по конкретным API endpoint-ам и HTTP методам.  
     
   - **Number of requests (RPS) per user:**  
     Выявление пользователей, создающих наибольшую нагрузку. Это может указывать на ботов, злоумышленников или неэффективное использование API.  
     - Ярлыки: user_id, endpoint, method – для детализации нагрузки по пользователям и API endpoint-ам.  
     
   - **Response time (latency):**  
     Оценка производительности API, выявление медленных запросов и улучшение клиентского опыта.  
     - Ярлыки: endpoint, method – для анализа времени отклика по конкретным API endpoint-ам и HTTP методам.  
     
   - **Number of HTTP 200:**  
     Оценка успешности запросов к API.  
     - Ярлыки: endpoint, method – для анализа успешности по конкретным API endpoint-ам и HTTP методам.  
     
   - **Number of HTTP 500:**  
     Выявление ошибок на стороне сервера, требующих анализа и исправления.  
     - Ярлыки: endpoint, method, error_message – для детализации ошибок по конкретным API endpoint-ам, HTTP методам и сообщениям об ошибках.  
     
   - **Number of simultaneous sessions:**  
     Мониторинг нагрузки на API и выявление аномалий.  
     - Ярлыки: instance, environment - помогает разграничить данные по различным инстанциям и окружениям, что важно для изоляции проблем.  
     
   - **Kb transferred (received/sent):**  
     Оценка сетевого трафика и выявление аномалий (DDoS).  
     - Ярлыки: instance, endpoint, method - позволяет анализировать трафик по инстанциям, конечным точкам и методам.  

3. **Compute Resources (Shop API, CRM API, MES API):**  

   Для оценки использования ресурсов будем отслеживать:

   - **CPU %:**  
     Оценка использования процессорного времени, выявление периодов высокой нагрузки и индикация необходимости масштабирования.  
     - Ярлыки: instance, environment – для анализа использования CPU по конкретным инстансам и окружениям.  
     
   - **Memory Utilisation:**  
     Оценка использования оперативной памяти, выявление утечек памяти и индикация необходимости масштабирования.  
     - Ярлыки: instance, environment – для анализа использования памяти по конкретным инстансам и окружениям.  

4. **Database Instances (Shop DB, MES DB):**  

   Для мониторинга баз данных будем отслеживать:

   - **Memory Utilisation:**  
     Оценка использования памяти, выявление нехватки памяти и индикация необходимости масштабирования.  
     - Ярлыки: instance, environment – для анализа использования памяти по конкретным инстансам и окружениям.  
     
   - **Number of connections:**  
     Мониторинг нагрузки на базу данных, выявление перегрузок и индикация необходимости масштабирования.  
     - Ярлыки: instance, environment – для анализа количества подключений по конкретным инстансам и окружениям.  
     
   - **Size:**  
     Размер базы данных, чтобы оценить необходимость масштабирования.  
     - Ярлыки: instance, environment.  

5. **Storage (S3 Storage):**  

   - **Size:**  
     Мониторинг использования хранилища 3D-моделей, прогнозирование затрат и предотвращение переполнения.  
     - Ярлыки: bucket_name – для анализа использования хранилища по конкретным бакетам.  

6. **Специфичные бизнес-метрики:**  

   - **Время расчета стоимости заказа в MES:**  
     Критичная метрика для мониторинга основной бизнес-функции, выявление медленных расчетов.  
     - Ярлыки: model_complexity, material – для анализа времени расчета по сложности модели и материалу.  
     
   - **Время выполнения задачи оператором в MES:**  
     Позволяет оценить эффективность работы операторов и выявить узкие места в производственном процессе.  
     - Ярлыки: task_type, operator_id – для анализа времени выполнения задач по типу задачи и оператору.  
     
   - **Количество заказов в каждом статусе:**  
     Позволяет отслеживать воронку заказов и выявлять проблемы на каждом этапе (например, застревание заказов в определенном статусе).  
     - Ярлыки: status – для анализа количества заказов по каждому статусу.  
     
   - **Количество активных пользователей в онлайн-магазине:**  
     Для оценки нагрузки и определения пиковых периодов активности, чтобы можно было планировать масштабирование.  
     - Ярлыки: Отсутствуют, так как в данном случае требуется общий показатель.  

   Этот список метрик является отправной точкой, и в процессе внедрения мониторинга и анализа данных могут быть добавлены новые метрики или изменены существующие. Главная цель – обеспечить полное и детальное представление о работе системы "Jewerly Store System" и использовать эти данные для ее оптимизации и улучшения.  

## План действий

1. **Выбор инструментов мониторинга:**  
   - **Prometheus:** Для сбора метрик из приложений и инфраструктуры.  
   - **Grafana:** Для визуализации метрик и создания дашбордов.  
   - **Alertmanager:** Для отправки уведомлений при возникновении проблем.  

   **Обоснование:** Комбинация Prometheus и Grafana является стандартом де-факто в индустрии и обладает широкой поддержкой сообщества. Они хорошо масштабируются и позволяют гибко настраивать сбор и визуализацию метрик. Alertmanager позволяет автоматизировать процесс реагирования на инциденты.  

2. **Настройка сбора метрик:**  
   - Внедрение Prometheus Exporter в каждый компонент системы (API, базы данных, RabbitMQ).  
   - Настройка Prometheus для сбора метрик из Exporter-ов.  

3. **Создание дашбордов Grafana:**  
   - Разработка дашбордов для каждой части системы, отображающих ключевые метрики.  
   - Настройка алертов для автоматического обнаружения проблем.  

4. **Обучение команды:**  
   - Проведение тренингов для команды разработки и поддержки по использованию инструментов мониторинга.  

5. **Итеративное улучшение:**  
   - Регулярный анализ данных мониторинга и внесение изменений в систему для улучшения ее производительности и стабильности.  

## Дополнительное задание: Показатели насыщенности и действия при превышении

Для автоматического реагирования на проблемы в системе "Jewerly Store System" важно определить показатели насыщенности ресурсов и пороговые значения, при превышении которых необходимо предпринимать определенные действия. Ниже представлено описание таких показателей и соответствующих действий.

1. **CPU Utilization (Использование процессорного времени):**  

   - **Метрика:** CPU % для Shop API, CRM API, MES API.  
   - **Пороговое значение:** 80% sustained (поддерживаемое) в течение 5 минут.  
     - Обоснование: 80% - это уровень, при котором система начинает испытывать замедления в обработке запросов. Удержание этого уровня в течение 5 минут указывает на устойчивую проблему, а не на кратковременный пик.  
   - **Действия при превышении:**  
     1. Создание тикета в Jira для отслеживания проблемы.  
     2. Автоматическое добавление нового инстанса EC2 (если настроено автомасштабирование) для увеличения вычислительной мощности.  
     3. Уведомление дежурного инженера для ручного анализа и принятия дополнительных мер.  

2. **Memory Utilization (Использование оперативной памяти):**  

   - **Метрика:** Memory Utilisation для Shop DB instance, MES DB instance.  
   - **Пороговое значение:** 90% sustained в течение 5 минут.  
     - Обоснование: 90% - это уровень, при котором база данных начинает активно использовать swap (если он есть), что приводит к значительному снижению производительности.  
   - **Действия при превышении:**  
     1. Создание тикета в Jira.  
     2. Увеличение размера инстанса базы данных (если возможно автоматическое масштабирование).  
     3. Уведомление дежурного инженера для ручного анализа (например, проверка на утечки памяти).  

3. **Message Queue Load (Загрузка очереди сообщений):**  

   - **Метрика:** Number of messages in flight in RabbitMQ.  
   - **Пороговое значение:** 10000 сообщений.  
     - Обоснование: 10000 сообщений - это уровень, при котором RabbitMQ может начать испытывать проблемы с производительностью и доставкой сообщений.  
   - **Действия при превышении:**  
     1. Создание тикета в Jira.  
     2. Увеличение количества потребителей сообщений (если возможно автоматическое масштабирование) для ускорения обработки очереди.  
     3. Уведомление дежурного инженера для анализа причин перегрузки и принятия дополнительных мер.  

4. **API Latency (Время отклика API):**  

   - **Метрика:** Response time (latency) for MES API.  
   - **Пороговое значение:** 2 секунды (95th percentile).  
     - Обоснование: 2 секунды - это приемлемое время отклика для большинства API запросов. 95th percentile позволяет игнорировать случайные медленные запросы и фокусироваться на улучшении общей производительности.  
   - **Действия при превышении:**  
     1. Создание тикета в Jira.  
     2. Анализ логов и профилирование кода для выявления медленных запросов.  
     3. Уведомление дежурного инженера для ручного анализа.  

5. **Расчет стоимости заказа в MES:**  

   - **Метрика:** Время расчета стоимости заказа в MES API.  
   - **Пороговое значение:** 10 минут для сложных моделей.  
     - Обоснование: Если расчет стоимости для сложных моделей занимает более 10 минут, это указывает на серьезные проблемы с производительностью.  
   - **Действия при превышении:**  
     1. Создание тикета в Jira.  
     2. Отправка уведомления команде разработки MES для анализа и оптимизации алгоритма расчета.  
     3. Автоматическое переключение на упрощенный алгоритм расчета (если он существует) для ускорения обработки заказа.  
     4. Уведомление дежурного инженера для ручного контроля.  

**Общие принципы реагирования:**  

- **Создание тикета в Jira:** Для отслеживания всех инцидентов и обеспечения прозрачности процесса решения проблем.  
- **Автоматическое масштабирование:** Для быстрого реагирования на увеличение нагрузки и предотвращения сбоев.  
- **Уведомление дежурного инженера:** Для решения сложных проблем, требующих ручного анализа и принятия нестандартных мер.  
- **Анализ и оптимизация:** Для выявления причин проблем и разработки долгосрочных решений.  

Важно отметить, что эти пороговые значения являются начальными и могут быть скорректированы в процессе эксплуатации системы и анализа данных мониторинга. Регулярный анализ данных и корректировка пороговых значений позволит создать более эффективную систему реагирования на инциденты.  

**Обоснование пороговых значений:**  

- Пороговые значения выбраны на основе анализа текущей производительности системы и с учетом запаса для предотвращения перегрузок.  
- Использование sustained values (например, "80% sustained for 5 minutes") позволяет избежать ложных срабатываний из-за кратковременных пиков нагрузки.  
- Выбор 95-го процентиля для времени отклика API позволяет учитывать outliers и фокусироваться на улучшении клиентского опыта для большинства пользователей.  

## Общие принципы реагирования на превышение пороговых значений:  

1. **Создание тикета в Jira:** Автоматическое создание тикета позволяет зафиксировать проблему и отслеживать ее решение.  
2. **Автоматическое масштабирование:** Автоматическое добавление инстансов или увеличение размера базы данных позволяет оперативно реагировать на увеличение нагрузки и предотвращать сбои.  
3. **Уведомление дежурного инженера:** Уведомление дежурного инженера обеспечивает оперативное реагирование на критические проблемы, которые не могут быть решены автоматически.  
4. **Анализ логов и профилирование кода:** Анализ логов и профилирование кода позволяет выявить причины проблем и разработать решения для их устранения.  
5. **Эскалация:** Если проблема не решается в течение определенного времени, необходимо эскалировать её вышестоящему руководству.  

Данный план действий позволит компании "Александрит" создать эффективную систему мониторинга, которая обеспечит стабильную работу, масштабируемость и улучшение клиентского опыта.
